# D2I 模板闭环精简改造（2026-07-30）

## 目标

这是个人项目，优先让“新网页 → 模板 → 抓图 → TITI 元数据 → 正式落盘”尽快跑通。

基本取舍：

- 抓错可以修模板后重抓。
- 不为形式完整强制三轮测试、双模式测试或大样本预生产。
- 不新建复杂模板平台，不引入新的数据库迁移。
- 只保留能明显减少误抓、重复劳动和 Build 猜接口的检查。

## 原问题

### 1. 能力已经存在，但没有接成一条线

D2I Lite 已有通用爬虫、模板、断点续跑、两种下载模式、TITI 元数据写入与回读质检。
`d2i-lite-template-builder` 也已经开发过，但只存在于旧 `main`/历史工作树，没有进入当前
`cloud` 分支的正式发布包。

### 2. Cloud 模板接口只实现了 list

Build 能列模板和建队，但不能通过正式接口完成：

```text
search → show → validate → import/update → run → outcome
```

这会迫使 Build 直接改只读发布目录、猜 API 路径或只在 Telegram 中保存临时结论。

### 3. 旧模板 Skill 与当前 Cloud 合同冲突

旧校验器要求 `image_url` 必填；当前合同要求无图人物也保留，因此必填只有
`name + detail_url`。旧 Skill 还会把长任务交给旧 worker / `d2i-jobs`，与 Cloud
主控模式冲突。

### 4. “保存生成模板”不是真正自动分析网页

桌面端该功能只是把当前运行配置保存为 JSON。网页结构分析和选择器生成仍应由
Build 的模板 Skill 完成。

### 5. 测试流程过重

旧流程默认结构轮、双模式轮、准生产轮，容易把个人项目拖成长期验收工程。多数公开人员页
抓错后可以低成本重抓，没有必要每站都做全套测试。

### 6. Telegram Bridge 提前吞掉最终结果

Bridge 原来固定等待 1800 秒。超时后即使任务仍是 `queued/running`，也会调用最终交付并写
`telegram_delivered`。真正结果稍后完成时，会被去重逻辑认为“已经发过”，因此用户只能看到
半成品或超时状态。

另外，Bridge 每秒发送 typing、每 12 秒刷新草稿，并且一轮内每个 progress 事件都强制更新
草稿，造成大量不必要的 Telegram 请求。

## 本次实现

### 持久模板经验库

新增 `cloud/template_service.py`：

- 内置模板继续随 release 只读发布。
- Build 导入和更新的模板写到：

  ```text
  ${D2I_CLOUD_DATA_ROOT}/templates/
  ```

- 模板说明和最近 50 次 outcome 写到：

  ```text
  ${D2I_CLOUD_DATA_ROOT}/template_registry/
  ```

- runtime 模板优先于同 ID 内置模板，发布切换不会丢失现场修复。
- 不增加新数据库和迁移。

### Cloud API

新增：

```text
GET   /api/v1/templates/search
GET   /api/v1/templates/{id}
POST  /api/v1/templates/validate
POST  /api/v1/templates
PATCH /api/v1/templates/{id}
POST  /api/v1/templates/{id}/outcomes
POST  /api/v1/templates/{id}/queues
```

### CLI

新增：

```text
d2i templates search --url <url>
d2i templates show <id>
d2i templates validate <template.json>
d2i templates import <template.json> [--overwrite]
d2i templates outcome <id> --stats <json> ...
```

同时修正 `d2i queues create`：省略 `--speed-tier` 时继承模板速度档，最终仍以 `safe`
作为兜底；不再由 CLI 强行覆盖成 safe。

### Build Skill

模板 Builder 进入 `cloud/skills/d2i-lite-template-builder/`，与 Cloud 同一个 release
发布、同一次安装更新。新规则：

- 新 URL 必须先 search。
- `image_url` 可选。
- 不再交给旧 worker / `d2i-jobs`。
- 默认只做一次结构校验和一个 5–10 人小样。
- 当前模式失败时才切换另一模式。
- 小站只有 1–6 人时允许直接全跑。
- 跑完写 outcome，保留真实经验。

### Telegram 回流

本地 `grok-build/telegram-bridge/bridge.py` 同步修正：

- 默认等待时间覆盖 Build 的 4 小时任务期限，不再固定 30 分钟。
- 等待超时时，只在任务已经进入真正终态时交付并标记 delivered。
- `queued/running/retry_wait` 超时时只通知“仍在运行”，不消费最终交付标记。
- sweep 继续每 20 秒补发真正终态，包含 cancelled。
- typing 降为最多每 4 秒一次。
- 草稿保活由 12 秒降为 25 秒一次。
- 同一轮多个 progress 事件合并后只更新一次草稿，并恢复增长量/时间节流。

## 日常最短流程

```text
1. d2i status
2. d2i templates search --url <URL>
3. Build 查看入口页、一个列表页、2–5 个详情页
4. 生成候选模板
5. d2i templates validate candidate.json
6. d2i templates import candidate.json --notes "站点特点"
7. 建一个 safe 小样队列
8. 看姓名、详情链接、图片；抽查一张 TITI 元数据回读
9. 正常就继续完整抓取
10. d2i templates outcome ...
```

遇到误抓：

```text
修模板 → import --overwrite → 新建队列重抓
```

不要求在旧队列上做复杂修复。

## 必须保留的少量检查

这些检查成本低，但能阻止最浪费时间的错误：

1. `list_item` 不能命中导航和栏目。
2. `name` 不能是“个人简历、要闻动态、市长、单位名”等。
3. 详情链接必须与人物对应。
4. 图片必须能打开，不能是 20×20 占位图或截断图。
5. 至少抽查一张成品图的 TITI 元数据回读。
6. `turbo` 必须明确确认。

除此之外，不强制做大样本、双模式和多轮形式验收。

## 部署后快速验收

只做以下检查：

1. `d2i status`
2. `d2i templates search --url <一个已有站点>`
3. `d2i templates show <一个已有模板>`
4. 校验并导入一个测试模板，再确认 `templates list` 可见
5. 写一条 outcome，再用 show 看得到
6. 删除测试用 runtime 模板和 registry 记录，或保留为明确标记的 smoke 模板

不启动真实大批量抓取，不跑全仓测试。

## 暂不做

- 模板 Web 管理页。
- CMS 指纹机器学习。
- 自动修复所有选择器。
- 每个站点固定三轮测试。
- 每个站点强制 `requests_jsl` 与 `browser` 对比。
- 为 outcome 新建复杂统计数据库。

这些能力只有在实际成为重复瓶颈时再做。
